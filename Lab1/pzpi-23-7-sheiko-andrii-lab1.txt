1. Бізнес вимоги
1.1. Передумови
Зростаюча потреба у комфорті та енергоефективності житлових і робочих приміщень робить затребуваними прості й доступні рішення для моніторингу та керування кліматом і освітленням. Багато користувачів хочуть віддалено контролювати стан кімнати (температура, вологість, освітленість) щоб приходити одразу у готову комфортну кымнату, і вмикати прилади без складних налаштувань.

1.2. Аналіз проблеми
У сучасних умовах значна частина людей прагне підвищити комфорт та енергоефективність житлових і робочих приміщень. Контроль температури, вологості та освітлення безпосередньо впливає на самопочуття, продуктивність та витрати енергії. Проте більшість традиційних підходів передбачає ручне керування або використання складних та дорогих систем «розумного дому».
Запропонована система «Smart Room» вирішує проблему відсутності доступних, простих та зрозумілих інструментів для моніторингу та дистанційного керування параметрами мікроклімату в одному приміщенні

1.3. Чому проблема є важливою
Відсутність автоматизованого контролю призводить до:
•	перевитрат електроенергії
•	зниження комфорту користувачів
•	необхідності постійної фізичної присутності для керування пристроям	
Система Smart Room дозволяє користувачам заздалегідь підготувати комфортні умови, отримувати актуальні дані в режимі реального часу та керувати пристроями віддалено
	
1.4. Аналіз аналогів
На ринку існують такі рішення, як Google Home, Apple HomeKit, Amazon Alexa та інші платформи «розумного дому». Їх основні недоліки в тому, що:
•	висока вартість
•	складність налаштування
•	залежність від закритих екосистем
•	надлишковий функціонал для базових потреб
На відміну від них, Smart Room орієнтований на простоту та відкритість

1.5. Можливості для бізнесу 
Існують великі платформи «розумного дому», але вони часто складні або платні. Простий студентський - локальний продукт, що поєднує IoT-модуль, веб-дашборд і мобільний застосунок, може служити демо-рішенням, освітнім проєктом або MVP для подальшого розвитку. Можливі шляхи монетизації в майбутньому: преміум-функції (правила автоматизації), інтеграція з голосовими помічниками, сервіс підтримки.

1.6. Цілі бізнесу та критерії успіху
БЦ1: розробити прототип Smart Room, що забезпечує моніторинг температури, вологості, освітленості та дистанційне керування освітленням	
БЦ2: надати веб та мобільний інтерфейс для відображення даних та керування
КУ1: демонстрація працездатності всіх ключових компонентів IoT → Backend → Frontend → Mobile на захисті проекту	
КУ2: мінімальний набір автоматизованих сценаріїв (наприклад, вмикати зволожувач при >30°C)
КУ3: стабільний запис показників у базу даних з інтервалом ≤ 30 сек у тестовому режимі
КУ4: досягти не менше 200 активних користувачів протягом перших місяців після запуску системи
КУ5: забезпечити стабыльну та коректну роботу основних модулів без помилок
КУ6: досягти певної маштабованості продукту після його запуску на ринку
КУ7: дати максимальну конкурентоспроможність на ринку після 9 місяців релізу

1.7. Потреби клієнта або ринку
П1: простий інтерфейс для перегляду поточних показників.
П2: система повинна мати українську локалізацію.
П3: можливість розширення системи.
П4: простий UX без зайвих налаштувань.
П5: можливість дистанційного вмикання/вимикання світла.
П6: графічна історія показників за вибраний період, історія показників (графіки) для аналізу (температура, вологість).
П7: надійність передачі даних IoT → сервер.
П8: можливість базової автоматизації (правила на сервері).
П9: безпека доступу (авторизація) та захист особистих даних.

1.8. Бізнес-ризики
•	Ризик 1: конкуренція з великими платформами розумного дому.
Серйознасть: середня. Існує ризик, що новий продукт не зможе швидко залучити користувачів.
Пом'якшення: фокус на простоті й локальному демонстраційному рішенні.
•	Ризик 2: проблеми з апаратною частиною (недоступні датчики або поломки).
Серйозність: низький-середній. Можлива недостатня проробка апаратної частини.
Пом'якшення: використовувати відомі компоненти (ESP32, DHT22).
•	Ризик 3: складності з мережевим підключенням Wi-Fi в умовах демонстрації.
Серйозність: висока. Часте відключення електроенергії.
Пом'якшення: тестування на локальній мережі та симуляція даних.
•	Ризик 4: проблеми безпеки (незахищені API).
Серйозність: висока.
Пом'якшення: базова аутентифікація, HTTPS на етапі деплою (опціонально), мінімальні права доступу.

2. Бачення рішення
2.1. Окреслення концепції	
Smart Room - легка система, що складається з IoT-пристрою (ESP32 + датчики), бекенду з REST API, веб-дашборду (React) та мобільного застосунку (Flutter або React Native). Система збирає показники температури, вологості і освітленості; зберігає їх; відображає графіки; дозволяє вмикати/вимикати лампу віддалено; має базову автоматизацію.
	
2.2. Призначення системи
Програмна система Smart Room призначена для збору, збереження, аналізу та відображення даних з IoT-сенсорів, а також для дистанційного керування освітленням у приміщенні. Система створює цінність для користувачів шляхом підвищення комфорту, зменшення ручних операцій та оптимізації енергоспоживання.
	
2.3. Опис бізнес-логіки
цБізнес-логіка системи полягає у наступному:
1.	IoT-пристрій періодично зчитує показники температури, вологості та освітленості. 
2.	Дані надсилаються на серверну частину через REST API або MQTT.
3.	Сервер зберігає дані у базі даних та застосовує правила автоматизації.
4.	Користувач через веб або мобільний інтерфейс:
o	переглядає поточні та історичні показники;
o	вмикає або вимикає освітлення;
o	отримує інформацію про стан системи.

2.4. Основні особливості
Ф1: збір даних від датчиків (температура, вологість, освітленість).
Ф2: вибір мови інтерфейсу (українська / англійська).
Ф3: відправлення даних на бекенд (HTTP POST або MQTT).
Ф4: REST API для отримання поточних та історичних даних.
Ф5: веб-інтерфейс з графіками та кнопками керування.
Ф6: мобільний додаток зі схожим інтерфейсом.
Ф7: базова логіка автоматизації (правила на бекенді).
Ф8: авторизація доступу до інтерфейсів (мінімально — простий логін).

2.5. Припущення і залежності
•	Припущення: користувач має Wi-Fi мережу в локації пристрою
•	Залежності: наявність ESP32, DHT22, LDR, реле; сервер (локальний чи хмарний) для бекенду; база даних (SQLite або MongoDB)
•	Відсутність необхідності інтеграції зі сторонніми комерційними IoT-платформами у першому релізі

3. Сфера застосування та обмеження
3.1. Початковий випуск (MVP) 
Включає мінімальний набір функцій, достатній для демонстрації:
1.	Збір та відправлення показників: температура, вологість, освітленість
2.	Збереження показників на сервері
3.	REST API:
o	POST /api/sensors - дані від IoT
o	GET /api/sensors/latest - поточні показники
o	GET /api/sensors/history?from=...&to=... - історія
o	POST /api/light - вмикання/вимкання реле
4.	Веб-дашборд (React): відображення поточних значень, графік (темп/вологість) та кнопка керування світлом
5.	Мобільний застосунок (Flutter/React Native): перегляд поточних значень і кнопка керування
6.	Локальна автоматизація: правило «якщо температура > X → вмикнути вентилятор» (опціонально реалізувати як симуляцію)

3.2. Сфера дії наступних випусків
1.	Підтримка більшої кількості акторів (декілька датчиків/кімнат)
2.	Push-сповіщення у мобільному додатку
3.	Гнучкі користувальницькі правила автоматизації
4.	Інтеграція з голосовими помічниками або розширені сценарії (розклад)
5.	Дашборд з картою кількох кімнат/пристроїв

3.3. Обмеження та виключення
1.	Система не керує 220V навантаженням без додаткових заходів безпеки (критичні пристрої керуються на совість розробника)
2.	Початковий випуск не включає масштабовану хмарну інфраструктуру для тисяч пристроїв
3.	Не передбачено машинне навчання або складну аналітику у першому релізі
4.	Система не виконує медичних функцій

4.3. Операційне середовище
Клієнт - серверна архітектура. IoT-пристрій підключається до локальної Wi-Fi мережі і відправляє дані на бекенд через HTTP (або MQTT). Сервер зберігає дані у локальній або хмарній базі даних. Клієнтські інтерфейси (веб та мобайл) запитують API для відображення даних.

5. Функціональні та нефункціональні вимоги
5.1. Функціональні вимоги (впорядковано за пріоритетом)
FR1: система повинна приймати дані від IoT пристрою (температура, вологість, освітленість).
FR2: система повинна зберігати показники у базі даних з позначкою часу.
FR3: API: POST /api/sensors - прийом даних; GET /api/sensors/latest - повернення останніх значень; GET /api/sensors/history - історія; POST /api/light - команда керування реле.
FR4: веб-інтерфейс повинен відображати поточні значення і графіки історії
FR5: веб-інтерфейс повинен дозволяти вмикати/вимикати світло (надсилати POST /api/light).
FR6: мобільний застосунок повинен показувати ті самі дані і дозволяти керування світлом.
FR7: бекенд повинен надавати прості правила автоматизації (адмініструються в конфігурації): наприклад, якщо temperature > T_on → on; < T_off → off.
FR8: система повинна логувати основні події (отримання даних, команди від користувача).

5.2. Нефункціональні вимоги
NFR1: система повинна обробляти оновлення від приладу з частотою до 1 разу на 10 секунд у локальних тестах.
NFR2: втрата одного повідомлення не повинна призводити до збою системи; повторні спроби передачі мають здійснюватись на стороні IoT.
NFR3: доступ до API має бути захищено базовою автентифікацією (наприклад, токен). Конфіденційні налаштування не зберігаються у відкритому вигляді.
NFR4: веб - інтерфейс має коректно відображатися в сучасних браузерах; мобільний додаток - на Android/iOS (через Flutter/React Native)
NFR5: IoT - код має легко перенастроюватися під інші сенсори
NFR6: для прототипу - обмежена; архітектура має бути такою, щоб у майбутньому можна було замінити SQLite на MongoDB та розгорнути бекенд у хмарі

6. Архітектура системи та компоненти
6.1. Компоненти
1.	IoT (ESP32): DHT22 (температура/вологість), LDR (освітленість), реле (керування лампою). Підключення до Wi-Fi; поведінка: періодичне відправлення POST /api/sensors + отримання команд GET /api/light/status (або підписка MQTT).
2.	Backend: ASP.NET Web API — REST API, база даних (SQLite для MVP), логіка правил, простий механізм автентифікації.
3.	Frontend (React): відображення даних, графіки (Chart.js/Recharts), кнопки керування.
4.	Mobile (Flutter/React Native): ті ж функції, спрощений інтерфейс під телефон.

6.2. Функціональні компоненти системи
Серверна частина та IoT-клієнт
Серверна частина виконує такі завдання:
•	прийом сенсорних даних;
•	збереження даних у базі;
•	реалізація REST API;
•	виконання базових правил автоматизації;
•	логування подій.
IoT-клієнт виконує такі функції:
•	зчитування даних з датчиків;
•	передавання даних на сервер;
•	отримання команд керування;
•	повторну відправку даних у разі збоїв зв'язку.

6.3 Веб-клієнт та мобільний клієнт
Веб-клієнт забезпечує:
•	відображення поточних значень;
•	побудову графіків історії;
•	керування освітленням.
Мобільний клієнт забезпечує:
•	перегляд сенсорних даних;
•	керування світлом;
•	доступ до системи з мобільних пристроїв.
Обидва клієнти взаємодіють із сервером через REST API

6.4 Технологічний стек
У проєкті використовуються наступні технології:
•	IoT: ESP32, DHT22, LDR, реле
•	Backend: ASP.NET Web API
•	Frontend: React
•	Mobile: Flutter або React Native
•	База даних: SQLite (MVP)
•	Протоколи: HTTP REST, MQTT (опціонально)
•	Контроль версій: Git, GitHub
•	IDE: Visual Studio, VS Code

6.5 Програмні засоби та інструменти
•	Git, GitHub - для контролю версій та зберігання коду.
•	Visual Studio, VS Code - як інтегровані середовища розробки.
•	Postman, Swager - для тестування API
•	Chart.js / Recharts - для побудови графіків у веб-інтерфейсі

6.6 Протоколи та інтерфейси
•	HTTP REST API (JSON).
•	Можлива альтернатива - MQTT для більш "реального" IoT (опціонально).
•	Бекенд відповідає JSON-повідомленнями; клієнти використовують Axios/fetch для веба та HTTP-клієнт у мобайлі.

7. План впровадження (релізи та етапи)
Реліз 1 (MVP) – 6 - 8 тижнів (орієнтовно)
•	Етап 1 (1-2 тижні): аппаратна частина — ESP32 + DHT22 + LDR + реле; базова прошивка (зчитування + POST).
•	Етап 2 (1-2 тижні): Backend — реалізація REST API, збереження в SQLite, базове тестування через Postman.
•	Етап 3 (1-2 тижні): Frontend — React-дашборд з відображенням поточних значень і графіком; кнопка керування світлом.
•	Етап 4 (1-2 тижні): Mobile — мінімальний застосунок з переглядом значень та кнопкою керування.
•	Етап 5 (1 тиждень): інтеграція, тестування, підготовка презентації.
Реліз 2 (опціонально)
•	Push-сповіщення, більш гнучкі правила автоматизації, підтримка декількох пристроїв/кімнат, перехід на MongoDB/хмарний хостинг.
